# PRD: Google サインイン（Web 先行）

- **Author**: motoshi.suzuki
- **Reviewers**: TBD
- **Last Updated**: 2026年6月23日
- **Status**: Draft
- **Project**: quran-project / Tilawah 認証

## 1. 背景と課題

Tilawah Web のサインアップに Google サインインを追加し、新規ユーザーの登録摩擦を下げる。

現状の Tilawah Web のサインアップ・サインインは email + password の一手段のみである（[ADR 0010](../adr/0010-auth-email-password.md)）。新規ユーザーはパスワードの設定と記憶を強いられ、これが初回登録の摩擦になる。サインアップ画面には Google ボタンの枠が無効状態で置かれているが（`apps/web/app/[locale]/(auth)/OAuthButtons.tsx`）、機能していないため、ユーザーの「Google で始めたい」という期待に応えられていない。

ADR 0010 は Google / Apple サインインを「post-launch の secondary path」として意図的に延期し、再検討トリガーの一つに「federated identity が要件化したとき」を挙げていた。本変更はこのトリガーを発火させ、延期されていた Google サインインを Web で実現する。パスワードを設定せずに Google アカウントだけでサインアップとサインインを完結できる状態を Web で提供することが、登録摩擦の低減という狙いの中身である。

## 2. 要件

### Step 1: Google でサインアップ・サインインできる

ユーザーは Web のサインアップ画面およびサインイン画面で「Google で続ける」を選び、Google アカウントで認証を完了できる。認証後、ユーザーは email + password ユーザーと区別なく、同一のセッションで以降のすべての機能を利用できる。

### Step 2: Google のみのユーザーが既存ユーザーと同等に扱われる

パスワードを一度も設定せず Google だけで登録したユーザーも、練習履歴・スコア・プロフィールなど、email + password ユーザーと同じデータと機能を持つ。Google のみのユーザーであることが、機能の制約や別扱いを生んではならない。

### Step 3: Google サインインの動作を運用上監視できる

Google サインインの結果（新規登録・既存ログイン・連携成立・連携要求）を区別して記録し、サインインの成功・失敗や連携要求の発生頻度を運用上監視できる。設定ミスや障害の兆候（例: 連携要求の急増）を検知する手がかりを残すための要件であり、利用状況の KPI 計測は目的としない。

### 非機能要件 N1: アカウント連携は本人性を確認できる範囲でのみ行う

既存の email + password アカウントと同じメールで Google サインインした場合、システムは本人性を確認できる範囲でのみ両者を同一アカウントとして扱う。本人性を確認できない場合は、勝手に統合せず、ユーザーに既存の手段での認証を求める。これはアカウント乗っ取り（pre-account hijacking）を防ぐための要件である。

## 3. 責務の境界

| 主体         | 責任                                                                                  |
| ------------ | ------------------------------------------------------------------------------------- |
| ブラウザ     | Google から本人を表す認証情報を取得し、Web サーバーへ渡す                             |
| Web サーバー | 認証情報を BFF へ中継し、発行されたセッションを安全に保持する。連携要求時の画面を出す |
| BFF          | 認証情報の真正性を検証し、アカウントの特定・作成・連携を判定し、セッションを発行する  |
| Google       | 本人認証と、メール検証状態を含む認証情報の提供                                        |

## 4. リスクと前提条件

- 前提: 既存の email + password アカウントは登録時にメール所有を前提に発行されている。N1 の安全な連携は、この前提に依存する。
- 前提: セッション（アクセストークン・リフレッシュトークン・cookie）の基盤は ADR 0010 / ADR 0011 で確立済みで、本変更はこれを再利用する。
- リスク: メール配信基盤が未整備のため、連携成立を本人へ即時にメール通知できない。本変更では構造化ログで記録し、検知の手がかりを残す。
- リスク: Google の認証情報検証は Google 側サービスへの到達性に依存する。Google 側障害時は Google サインインのみ失敗し、email + password 経路は独立経路として影響を受けない。
